# MFA 因素轮换与受控恢复

2026-10-20。P2 增量，实现 TOTP 因素的自助轮换及管理员授权恢复。当前不包含 AES 加密主 key 在线重加密、硬件认证器、恢复码、自动身份核验或通知渠道；不能以本地用例代替企业恢复流程验收。

## 正常因素轮换

用户先完成密码登录与当前因素验证，两者均须距今不超过五分钟，再调用轮换接口。服务生成新的随机 160 位 TOTP 密钥，返回一次 Base32/otpauth URI；数据库保存 AES-GCM 密文，绑定本人 UUID。轮换记录同时绑定当前 epoch、浏览器 session 摘要和五分钟有效期。

旧因素在 pending 期间继续有效。新建轮换会 supersede 本人的旧 pending，旧 pending 的密文清空。确认新因素成功后，在一个 PG 事务内替换活动因素、消费新因素时间步、清空 pending 密文、递增 epoch、撤销授权族并消费旧挑战。旧会话和令牌失效，用户重新密码登录并使用新因素完成 MFA。提交失败则全部回滚，原因素仍有效，同一 pending 可重试。

同一 pending 只能由创建它的浏览器确认或取消。轮换开始后再做会话 ID 轮换会使该 pending 不可使用，应先完成 MFA 再开始因素轮换。取消或过期不修改活动因素；后台默认每五秒把过期 pending 标为 EXPIRED 并清空密文，接口本身仍即时检查过期时间，不依赖扫描放行。

新因素确认失败计数持久化在独立用户 guard：五次失败锁三十分钟，新建 pending、换浏览器、重新登录或管理员重新授权均不能清零。成功确认才清零。常规 TOTP 登录挑战原有的失败计数与时间步防重放继续保留。

## 丢失因素后的受控恢复

恢复需要另一位操作员。操作员必须有实时 `ROLE_ADMIN_MFA_RECOVERY`、近期密码登录和近期 MFA；禁止自我授权。请求要求原因、外部核验凭据引用与 Idempotency-Key。引用由操作员按企业流程核验，服务只验证格式并持久记录，**不会自动证明核验事实成立**。目标须 ACTIVE/OPEN 且已启用因素或正处于因素恢复中；密码操作仍处于 BLOCKED 时先解决该操作。

授权在一个事务内完成：

1. 按 PG UUID 顺序锁定操作员和目标身份，复核操作员状态、epoch、权限与认证时间。
2. 撤销目标已有恢复凭证，清空旧 pending 密文，退役活动因素。
3. 设置持久 `mfa_recovery_required=true`，递增 epoch、撤销所有授权族、消费旧挑战。
4. 生成随机 256 位恢复凭证，只保存 SHA-256 摘要，绑定目标新 epoch、签发操作员及其 epoch、十五分钟期限、原因和核验引用。明文只返回一次，DTO 字符串表示脱敏。

相同操作员、目标、幂等键及原因/证据重试返回同一记录，`token=null`，不会再次递增 epoch，也不能从摘要恢复明文；更改原因或证据返回 409。响应丢失时，需要操作员以新键重新核验授权，之前的凭证随之撤销。

操作员通过已核验的可信渠道向员工交付一次性凭证。当前代码不自动发送这类凭证，不复用邮件密码重置 proof，也不接受客户端提交的 actor、权限或 MFA 时间作为授权依据。自动通知、工单系统和渠道联调仍属后续工作。

员工重新密码登录后，将凭证作为 JSON body 交给恢复接口。服务校验目标归属、目标 epoch、有效期、一次性消费状态，以及签发操作员当前 ACTIVE/OPEN、epoch 和实时权限。成功消费后生成同浏览器绑定的新因素 pending，其有效期取五分钟和凭证剩余期限的较早值。确认前再次检查操作员和凭证状态；操作员权限撤销、账号禁用或 epoch 变化都会拒绝后续步骤。

恢复期间普通注册入口拒绝覆盖因素，授权和 JWT 签发均保持 MFA 限制。只有新因素确认成功才清除 `mfa_recovery_required`，并再次递增 epoch、撤销族，要求重新认证。取消、过期、密码重置和进程重启都不会自动解除恢复标志。pending 响应丢失、会话变更或取消后，一次性凭证仍已消费，必须重新取得授权；不能通过删除数据库标志绕过恢复。

## HTTP 契约

这些是认证后的 IAM 浏览器接口，所有 POST 要求 CSRF。敏感响应保持 `Cache-Control: no-store`；不得把恢复凭证或 TOTP 密钥放在 URL query、审计、日志或浏览器持久存储中。完整契约见 [OpenAPI](openapi.json)。

| 方法与路径 | 请求 / 返回 |
|---|---|
| `GET /api/mfa` | 增加 `recovery_required`，仅返回本人因素状态 |
| `POST /api/mfa/rotation` | 返回 `id, secret, otpauthUri, expiresAt` |
| `POST /api/mfa/recovery` | `{ "recovery_token": "一次性凭证" }`；返回同上 |
| `POST /api/mfa/changes/{id}/confirm` | `{ "code": "六位数字" }`；返回 `reauthentication_required=true` |
| `POST /api/mfa/changes/{id}/cancel` | 取消本浏览器 pending，返回 `cancelled=true` |
| `POST /api/admin/mfa/users/{id}/recovery` | Idempotency-Key 与 `{ "reason": "核验说明", "evidence_ref": "ticket:..." }`；返回 `id, token, expiresAt`，重复时 token 为 null |

非法、过期或错误归属操作返回 400；缺少近期认证、权限或自我恢复返回 403；目标 gate 冲突或幂等内容变更返回 409；五次确认失败后返回 429。过时会话由安全过滤器返回 401，依赖查询失败拒绝放行。恢复标志独立于密码 gate，仍允许受认证的状态查询和恢复因素操作，不代表可用密码单独签发令牌。

## 数据、审计与回退

V7 新增 `mfa_recovery_grant`、`mfa_factor_change`、`mfa_lifecycle_guard` 与身份恢复标志。恢复记录保存操作员、目标、epoch、原因、证据、消费/撤销与到期时间；因素变更保留状态和时间，不保留终态 pending 密文。认证审计记录开始、失败、成功及取消动作，不保存验证码、明文密钥或恢复凭证。长期保留、清理与通知策略需在 T8/T11 继续落地。

身份在因素、凭证、pending 和授权族之前加锁；跨用户恢复使用与 Redis 全局恢复一致的 PG UUID 顺序。数据库事务提交后才返回恢复秘密，失败不会留下已退役但无恢复标志的中间状态。

部署必须完成 V7 迁移并升级全部签发节点。旧版本不理解恢复标志；存在恢复中用户时不能直接回退旧签发代码。退回之前需要停止签发、盘点恢复记录、完成或重新批准恢复，并验证所有资源端状态检查；删除表或清空标志不构成安全回退。
