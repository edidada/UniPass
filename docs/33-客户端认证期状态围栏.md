# 客户端认证期状态围栏（N1，P0）

> 本增量关闭「客户端已通过入口 `ClientStatusFilter` 后、停用/轮换事务提交、认证仍用旧状态签发 token」的竞态。状态为**编码增量**，未经本地构建，仅由远程 CI 验证；见 CI 绿灯前不标记完成。

## 1. 背景与竞态

- `ClientStatusFilter` 在协议入口按 `oauth_client_status.disabled` 阻断 `authorize`/`token`/`introspect`/`revoke`，属于**入口检查**，不身处认证事务内。
- 停用/轮换（`ClientAdminService.setEnabled`/`rotate`）对 `oauth2_registered_client` 注册行加 `FOR UPDATE` 锁并写入 `oauth_client_status`，但认证路径（框架 `ClientSecretAuthenticationProvider` + `PreviousClientSecretAuthenticationProvider`）读取的是已提交态，与停用事务**不串行**。
- 竞态窗口：请求通过入口过滤器 → 停用事务提交（置 `disabled=true`）→ 认证仍用提交前的「未禁用 + 旧 secret」签发 token。

## 2. 设计

新增 `FencedClientSecretAuthenticationProvider`，仅处理 `client_secret_basic` 与 `client_secret_post`：

1. 开启一个 `TransactionTemplate` 事务。
2. `SELECT id FROM oauth2_registered_client WHERE client_id=? FOR UPDATE`；无行 → 返回 `null`，交给默认 provider 产生 `invalid_client`。
3. 读 `oauth_client_status.disabled`（无行视为启用）。
4. **disabled 优先**：在比较任何 secret 之前直接抛 `OAuth2AuthenticationException(INVALID_CLIENT)`，不泄露原因（fail-closed）。
5. 用 delegating password encoder 校验当前 `client_secret`；失败时仅在 `oauth_client_secret_previous.valid_until > now` 窗口内校验前序 hash；都失败抛 `invalid_client`。
6. 校验 `client_secret_expires_at`（若存在且已过 → 拒）。
7. 按框架 `CodeVerifierAuthenticator` 语义校验 authorization_code 的 `code_verifier`（经 `OAuth2AuthorizationService` 读取授权，不得放宽/跳过）。
8. 返回 `OAuth2ClientAuthenticationToken(registeredClient, method, credentials)`。
9. 事务提交后行锁释放，确保与停用/轮换串行。

该 provider 在 `SecurityConfiguration` 中注册于客户端认证链**最前**；保留 `nativeClients`（`NONE`/refresh）、`previousSecrets`（前序密钥回退），非 secret 方法（JWT 断言等）仍由默认 provider 处理。

### 公共客户端（NONE）第二道防线

`NativeRefreshSupport.authenticate`（公开 native 客户端 refresh 的签发入口）增加「已停用则拒绝」守卫：仅读 `oauth_client_status.disabled`（无行视为启用），命中则抛 `invalid_client`。**仅读状态、不对注册行加锁**，避免与禁用事务形成反向锁序而死锁。

## 3. 锁顺序（统一，禁止反向）

所有涉及「注册行 + 状态」的路径一律：

1. 先对 `oauth2_registered_client` 注册行 `FOR UPDATE`；
2. 再读 `oauth_client_status`。

- 认证围栏：步骤 2 → 步骤 3，顺序正确。
- 禁用/轮换：`ClientAdminService.locked()` 先锁注册行，再写 `oauth_client_status`/`oauth2_authorization`，顺序一致。
- 公共客户端守卫：只读 `oauth_client_status`，不持注册行锁，不存在反向锁序。

PKCE 读取 `oauth2_authorization` 发生在上述两步之后，不破坏该顺序。

## 4. fail-closed 边界

- 未知客户端：`null` → 默认 provider 产生 `invalid_client`（不自行判定，避免信息差异）。
- 已禁用：任何密钥比对前即拒，不区分原因。
- 当前/前序密钥均不匹配、密钥过期：拒。
- 非 authorization_code 授权：跳过 PKCE（不误伤 `client_credentials`/`refresh_token`）。
- PKCE：`code_challenge` 缺失且 `requireProofKey=true` 或误带 `code_verifier` → `invalid_grant`；S256 不匹配 → `invalid_grant`。

## 5. 覆盖与未覆盖

| 项 | 覆盖 |
|---|---|
| 停用 + 当前密钥 → 拒；启用 + 当前密钥 → 成功 | `ClientStateFenceIT` |
| 前序密钥窗口内 → 成功；窗口过期 → 失败 | `ClientStateFenceIT` |
| 停用事务与认证在注册行上并发串行（B 阻塞至 A 提交后失败） | `ClientStateFenceIT`（latch + 超时，测试结束清理线程） |
| PKCE 正确/错误/缺失 verifier（含 `requireProofKey=true` 机密客户端） | `ClientStateFenceIT` |
| 公共客户端已停用刷新拒绝 | `NativeRefreshSupport` 守卫（通过 `ClientStatusFilter` 与入口已覆盖，单元覆盖见 §6 限制） |

**未覆盖 / 限制**：

- 入口过滤器与事务围栏的关系：两者并存、职责互补——过滤器挡住新请求入口，事务围栏在认证内对实时禁用态做串行化复核；本增量不删除过滤器。
- 公开客户端守卫的单元断言依赖嵌入式 PG 中已有的 `oauth_client_status` 读取路径，未单独起负向 IT（入口过滤器已挡住协议端点）；如后续需要可补 `ClientStateFenceIT` 用例。
- 未发生「停用后清除前序窗口」或「围栏未投递 `oidc_logout_task`」的产品决策（见 `docs/32` N2/N3），本增量不涉及。
- 全量 67 项 `OidcFlowIT` 与 8 项 `ClientManagementHttpIT` 须保持通过；如有夹具需适配，仅做最小修改。
